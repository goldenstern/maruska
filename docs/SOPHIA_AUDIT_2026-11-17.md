## 1. Резюме

Фреймворк уже содержит сильную предметную модель: конечный автомат задач, детерминированные гейты, отдельные модули CPU / опыта / активности / ипостасей и проверяемые инварианты. Главный архитектурный долг сейчас не в «недостатке ИИ», а в границах владения состоянием: несколько процессов/инстансов читают и пишут общие файлы, но часть согласования, идентификаторов и реактивного обновления остаётся локальной для одного процесса.

В этой фазе сделаны ограниченные, проверяемые изменения:

- `ServerGuard` вынесен из `index.ts` в `server_guard.ts`; экземпляр теперь принадлежит конкретному `Plugin.setup(root)`, а не разделяется глобальной переменной между проектами.
- `saveLedger` защищён точной сигнатурой содержимого и межпроцессным lock-файлом; запись использует уникальный temp-файл, `fsync` и атомарное переименование.
- добавлена защита от перезаписи последней валидной `.bak` повреждённым primary-файлом.
- исправлены три ошибки `ServerGuard`: позиция очереди считалась глобально; оставшиеся ожидающие терялись при передаче брони; новая реализация сохраняет FIFO-хвост.
- явный `model_reset` теперь обнуляет и `upstream_streak`.
- тесты больше не зависят от абсолютного Windows-пути разработчика и не создают артефакты в корне репозитория.
- добавлены `npm run test`, `npm run gate`, `npm run check`; приведены в соответствие тестовая команда и правило перезапуска плагина в документации.

**Важно:** это не полный распил двух монолитов и не окончательное закрытие T164/T184. Остаточные гонки ID, семантика merge для счётчиков/удалений и реактивность панели оставлены отдельными задачами ниже. Их нельзя скрывать за зелёным тестовым прогоном.

## 2. Что было проверено

В архиве присутствовали исходники, тесты и архитектурные документы. Не присутствовали `.git`, `DEVATA/state.json`, `DEVATA/CONSOLE_UI.html`, `panel_channel.json`, ключи и активное состояние процесса.

Следствия:

- можно провести статический аудит кода и воспроизводимые тесты на временных файлах;
- нельзя достоверно воспроизвести живой инцидент T184, проверить текущие runtime-порты и увидеть межпроцессную картину именно того инцидента;
- нельзя создать git-коммит или доказать чистоту/состояние рабочей ветки; архивная копия и патч подготовлены отдельно;
- Windows/PowerShell-ветки (SendMessageTimeout, tasklist/netstat, spawn PowerShell) не исполнялись в этой среде.

## 3. P0 · целостность ledger (T164)

### Что было не так

Старый штамп основывался на `updated_at`. Это не уникальный CAS-токен: две записи в одну миллисекунду могут сохранить одинаковое значение. При загрузке ещё не существующего файла держатель также не получал baseline-маркер. В результате первый независимый writer мог перезаписать запись другого writer целым снимком.

### Что изменено в Phase 1

`state.ts`:

1. `loadedStamp` хранит SHA-256 точного содержимого, прочитанного при `loadLedger`; для отсутствующего файла хранит `null`.
2. `saveLedger` берёт lock конкретного файла через `state.json.lock` (`open(..., "wx")`), ждёт освобождения, проверяет PID/возраст и удаляет только просроченный lock мёртвого владельца.
3. Под lock сравнивается точный hash. При изменении файл повторно читается и сливается с локальным снимком.
4. Temp-файл уникален на процесс/вызов; содержимое сбрасывается через `fsync`; финальный `rename` атомарен.
5. Если ранее существовавший ledger исчез, старый снимок не воскрешает его молча.
6. Повреждённый primary не копируется поверх `.bak`: резервная копия остаётся пригодной для восстановления.

### Верификация

- тест изменения содержимого при неизменном `updated_at`;
- тест создания файла после пустой загрузки;
- тест восстановления из backup без порчи backup;
- отдельный стресс-прогон: 8 независимых процессов загрузили один baseline, одновременно сохранили по уникальной записи; итог — 8/8 записей, lock-файл удалён.

### Что всё ещё НЕ решено

**P0-A · гонка `max+1` при выделении ID.** `nextTaskId` / `nextAgentId` вычисляют следующий ID по локальному снимку до `saveLedger`. Lock на сохранении не делает саму аллокацию транзакционной. Два независимых процесса могут получить один `T###` / `A###`; слияние по ID сочтёт их одной сущностью. Тест первого сохранения намеренно использует разные ID и не доказывает безопасность аллокатора. Нужна отдельная атомарная резервация ID либо единая транзакция «прочитать → выделить → записать».

**P0-B · счётчики моделей.** `mergeModels` объединяет `ok`, `fail`, `upstream_fails`, `upstream_streak`, `byClass.*` через `Math.max`. Это предотвращает откат, но теряет два независимых инкремента от общего baseline (10 + 1 и 10 + 1 превращаются в 11, а не 12). Кроме того, `Math.max` не позволяет надёжно распространить сброс `upstream_streak` через stale writer; более поздний merge может вернуть старое значение. Нужны baseline/delta-семантика, revision/epoch сброса или append-only события. Нельзя просто заменить `max` на сложение: тогда повторный merge одного снимка задвоит счёт.

**P0-C · удаления без tombstone.** `mergeById` соединяет массивы по ключу и `updated_at`, но отсутствие записи не является явным удалением. Удалённый/схлопнутый агент может вернуться из stale-снимка. Нужны tombstone/revision или событийная модель удаления.

## 4. P0 · застывание панели (T184)

### Установленные факты из кода

- `renderPane(ledger)` строит HTML-проекцию и записывает её в `DEVATA/CONSOLE_UI.html`.
- HTML обновляется при вызовах локального `save()`/рендера; у страницы есть meta-refresh примерно раз в 10 секунд.
- HTTP-обработчик `handlePanel` имеет `GET /probe` и POST-команды (`/wake`, `/blink`, `/order`, `/monitors-off`); отдельного `GET /state` в этом обработчике нет.
- `/probe` подтверждает доступность HTTP-канала/процесса и возвращает порт/время запуска; он не сверяет свежесть содержимого ledger или HTML.
- `stateVersion` и `stateSeen` — переменные конкретного `setup`, а не общепроектная revision.

### Вывод

Архитектурно возможна ситуация: `state.json` уже обновлён другим процессом, HTTP probe отвечает, но процесс-владелец панели не получил событие и не вызвал `renderPane`; HTML остаётся старым. Это согласуется с симптомами T184, но без живого `state.json`, HTML, `panel_channel.json` и журналов нельзя объявить это доказанной причиной конкретного инцидента.

### Следующий фикс (пока НЕ внесён)

Сначала утвердить модель владения: один канал на проект или канал на каждый OpenCode-процесс. Затем ввести durable `revision` состояния и реактивную инвалидацию проекции при изменении ledger извне: watcher + debounce или единый проектный координатор. UI должен получать текущую revision/снимок из общего источника, а probe должен отдельно показывать `transport_alive` и `projection_revision`/`ledger_revision`. Не добавлять синтетические ходы модели и не будить простаивающие сессии ради обновления панели.

## 5. P1 · модульность и владение

### Выполнено

`ServerGuard` (реестр серверов, probing, очередь и handoff) вынесен в отдельный `DEV_CONSOLE/server_guard.ts` — 370 строк. В `index.ts` экземпляр `ServerGuard` теперь создаётся локально внутри `Plugin.setup(root)`. Ранее это был модульный `let serverGuard`, который мог быть перезаписан setup другого проекта в том же процессе. После извлечения `index.ts` сократился с 4690 до 4330 строк.

Добавлен `server_guard.test.ts`: проверяет персистентность реестра, изоляцию двух root, локальный ранг ожидания, дедупликацию и сохранение оставшихся FIFO-waiters после handoff.

### Остаток

`state.ts` остаётся 6144 строками и смешивает типы, операции, политику моделей, миграции/санитизацию, persistence, merge и UI-проекцию. `index.ts` остаётся 4330 строками и смешивает OpenCode hooks, lifecycle, dispatch, HTTP-канал, feed, таймеры и side effects.

Рекомендуемый порядок распила без смены контрактов:

1. `ledger/types.ts` + `ledger/normalize.ts` — контракты и миграции/санитизация.
2. `ledger/persistence.ts` — lock, load/save, backup, merge; отдельные тесты на процессы и восстановление.
3. `ledger/operations.ts` — конечный автомат, ID-аллокатор и чистые доменные операции.
4. `models/policy.ts` — выбор, квоты, cooldown, статистика; только после решения delta/reset semantics.
5. `projection/console.ts` — `project` и HTML-рендер; тесты snapshot/контрактов UI.
6. В runtime: `panel_channel.ts`, `dispatch.ts`, `session_feed.ts`, `monitors.ts`; `index.ts` оставить composition root.

Каждый шаг — перемещение без переписывания алгоритмов, import-gate + весь suite, затем отдельная маленькая функциональная правка.

## 6. P1 · хранение и sidecars

Помимо `state.json`, в `index.ts` / `server_guard.ts` обнаружены sidecar-файлы, записываемые напрямую через `writeFileSync`: `servers.json`, `servers.queue.json`, `wake_keys.json`, `tab_topics.json`, `ritual_state.json`, а также diagnostics/render logs. Для реестров, очередей и state-файлов это создаёт риск частичной записи/гонки между экземплярами. Следующая задача — общий маленький `writeJsonAtomic` с уникальным temp + fsync + rename и при необходимости локальный per-file lock. Для append-only логов нужен отдельный формат, не замена тем же helper.

Не переводить всё в один «универсальный storage framework»: простой helper + ясный владельческий контракт предпочтительнее.

## 7. P1 · конфигурация и зависимости

- Корневой `package.json` запрашивает `@opencode/plugin ^2.0.20`; `DEV_CONSOLE/package.json` — `^2.0.22`; текущий `package-lock.json` закрепляет `2.0.20`. Нельзя автоматически обновлять без проверки API/runtime совместимости.
- `PIPELINE_PROJECT.md` содержал частичный тестовый прогон и ошибочное утверждение о hot-reload. Команды тестов обновлены на полный suite; процессный deploy-gate приведён к правилу из брифа: новый OpenCode-процесс, только после отдельного разрешения Основателя.
- Модельная конфигурация в `PIPELINE_PROJECT.md`, `LAVK DEVATA/SKILL.md` и коде содержит исторически разные списки/роли моделей. В этой фазе модельный пул не менялся: сначала требуется единое решение владельца и источник правды, иначе рефакторинг может незаметно изменить маршрутизацию/стоимость.
- Зависимость `@opencode/plugin` по package/lock metadata остаётся крупной. Сначала стоит измерить реальный runtime dependency graph и время старта; vendoring/замены не делать без API-совместимого прототипа.

## 8. P2 · качество и эргономика разработки

- Inline PowerShell в `index.ts` — вынести в маленькие PS1-ресурсы только после фиксации escaping/кодировки и тестов на Windows.
- Константы таймингов, grace/TTL, лимиты и UI-глифы — собрать в тематические модули без изменения значений/контрактов.
- Повторяющиеся строки/цвета/glyph-контракт между TypeScript и запечённым HTML требуют одного источника генерации; не делать синхронизацию двух копий вручную.
- Тестовые команды теперь один вызов `npm run check`; тесты жалоб пишут во временный каталог ОС и не загрязняют корень проекта.

## 9. P3 · производительность

## 12. Решение для следующей фазы

Следующая фаза должна начинаться не с косметического деления `state.ts`, а с трёх контрактов:

1. атомарный уникальный ID на уровне проекта;
2. корректная семантика совместного изменения счётчиков/сбросов/удалений;
3. revision + инвалидация панели между процессами.

После фиксации этих контрактов модульный распил станет безопаснее: фреймворк будет владеть координацией, а модель сможет оставаться тонким исполнителем.
