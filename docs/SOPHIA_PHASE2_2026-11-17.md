## 1. Результат

Phase 2 закрывает три обнаруженных класса риска ledger:

- **P0-A — уникальность ID:** резервирование `T###` и `A###` теперь атомарно между процессами и не зависит от свежести снимка в памяти.
- **P0-B — независимые изменения статистики:** счётчики моделей и `byClass` сливаются как дельты относительно baseline конкретного writer-а; повторное сохранение того же снимка не задваивает дельту.
- **P0-C — удаление дублирующегося агента:** удалённый при `rekeyAgent` дубль получает durable tombstone; merge и нормализация на чтении не возвращают его из устаревшего снимка.

Дополнительно обнаружен и исправлен double-count: runtime записывал общий результат модели через `recordModelResult`, а затем повторно инкрементировал общие счётчики внутри `recordModelResultByClass`. Теперь runtime вызывает per-class запись без повторного глобального инкремента; прежнее поведение оставлено по умолчанию для совместимости прямых callers.

## 2. Изменения по компонентам

### 2.1 P0-A — проектный аллокатор ID

`DEV_CONSOLE/state.ts`:

- Добавлен `reserveLedgerId(file, kind, observed)`.
- Резервации хранятся в отдельном sidecar `DEVATA/state.json.ids.json` с независимыми последовательностями задач и агентов.
- Для sidecar используется тот же межпроцессный lock-механизм с отдельным lock-файлом; запись — уникальный temp-файл, `fsync`, атомарный rename.
- При первом создании последовательность поднимается выше максимального ID из текущего снимка, основного ledger и валидного `.bak`.
- Если основной ledger повреждён, но backup валиден, верхняя граница берётся из backup. Если sidecar повреждён или имеет неизвестную схему, аллокатор **fail-closed**: он прекращает выдачу, а не рискует повторно выдать зарезервированный ID.
- Неудача последующего сохранения может оставить пропуск в последовательности. Это намеренно: идентификатор уникален, а не обязан быть плотным рядом.

`DEV_CONSOLE/index.ts`:

- `idFile: stateFile` передаётся в три production-пути создания агента.
- Команда создания задачи передаёт `stateFile` в `applyOp`.
- Старый формат идентификаторов `T###` / `A###` сохранён.

### 2.2 P0-B — baseline-aware merge статистики

`DEV_CONSOLE/state.ts`:

- При загрузке и после успешного сохранения фиксируется deep-clone baseline модели, включая `byClass`.
- `ok`, `fail`, `upstream_fails`, `byClass.ok/fail/runs/editsPerSecSum` объединяются по дельтам writer-а относительно его baseline.
- При известном пустом baseline два процесса, впервые создавшие одну и ту же запись модели, сохраняют оба независимых результата.
- После успешного сохранения baseline обновляется; повторный `saveLedger` того же снимка не добавляет уже учтённую дельту второй раз.
- Для `upstream_streak` добавлены timestamp reset/update, а для cooldown — timestamp изменения. Это позволяет явному сбросу побеждать устаревшее значение, не поднимая старый cooldown снова.

`DEV_CONSOLE/index.ts`:

- Устранён повторный глобальный инкремент на связке `recordModelResult` + `recordModelResultByClass`.

### 2.3 P0-C — tombstones

`Ledger` получил необязательный `tombstones` с картами для `tasks`, `agents`, `tabs`, `foreign_sessions`.

- `rekeyAgent` ставит tombstone для поглощённого дублирующего агента до удаления строки.
- `mergeLedger` объединяет tombstones и фильтрует ими результат слияния.
- `loadLedger`/нормализация применяет tombstones до формирования проекций, даже если файл временно содержит одновременно старую строку и маркер удаления.
- Старые ledger без поля `tombstones` продолжают загружаться; поле добавляется без обязательной миграции формата.

**Граница заявления:** в этом проходе фактически закрыт известный production-путь удаления дублирующего агента в `rekeyAgent`. Новые операции удаления задач/вкладок/foreign sessions при появлении должны также создавать tombstone; одной физической фильтрации массива для них недостаточно.

### 2.4 Защита приватных runtime-файлов

`.gitignore` расширен на `state.json*` и используемые runtime sidecars/снимки (`panel_channel.json`, `model_health.json`, `servers*.json`, `wake_keys.json`, `tab_topics.json`, `ritual_state.json`, `CONSOLE_UI.html`). Это снижает риск случайно опубликовать локальное состояние и файл ID-резерваций.

## 4. Обновление и эксплуатационные инварианты

1. **Не запускать смешанный набор writer-ов.** При переходе на Phase 2 все процессы, пишущие один и тот же `state.json`, должны работать на одной версии кода. Старый процесс не использует новый sidecar-аллокатор и может нарушить уникальность ID.
2. **Не удалять `DEVATA/state.json.ids.json`.** Это durable-счётчик зарезервированных ID. Удаление sidecar при существующем ledger может вернуть аллокатор к вычислению по текущим строкам и повторно выдать номер, который был зарезервирован, но не успел попасть в state.
3. Рядом с sidecar может кратковременно существовать `${stateFile}.ids.json.lock`; это служебная блокировка, не часть состояния и не файл для ручного редактирования.
4. Перед применением в рабочее окружение: сохранить backup ledger и sidecar вместе; остановить/заменить все старые writer-процессы в согласованном окне; проверить `/api/session/active`; запускать новый OpenCode-процесс только после отдельного разрешения Основателя.
5. Этот пакет **не запускает** сервис и не касается живого `DEVATA/state.json`.
